# 交接：到点提醒（电脑端已完成，终端待接）

> 一句话：电脑端现在能回答「**现在该念什么**」，终端只要每隔几分钟问一次，
> 按 `remind_id` 去重，按模板念出来。
> 判定规则全在电脑端（只有这边知道条目、隐藏、已交状态、时间窗），
> 念的时机全在终端（只有那边有喇叭、知道现在闲不闲）。

## 二、新接口：`GET /api/remind`

### 2.1 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `stage` | 空 | `morning` / `evening` / `soon`，只看一个位；填错给 400 |
| `preview` | `0` | `1` 时三个位都算一遍，**不管现在几点**（调试、演示、答辩现场用） |
| `limit` | `8` | 每个位最多几条；超过的标 `truncated` 并给 `dropped` |

鉴权和别的 `/api/*` 一样：本机访问不要口令；局域网要 `X-Access-Key`（或 `?key=`）。
这个接口**不发任何网络请求**，只用本机已存的数据（Canvas 用上次抓取的缓存）——
早上八点网还没连上时，它照样答得出来。

### 2.3 字段说明

顶层

| 字段 | 含义 |
|---|---|
| `now` | 服务端现在的时刻（带 `+08:00`）。终端拿它校准，不用自己算 |
| `stages` | 现在到点的提醒位，**按念的顺序排好**：`soon` → `morning` → `evening` |
| `due_count` | 有几个位到点了 |
| `count` | 所有位加起来几条 |
| `settings` | 生效的提醒设置（下面「四」讲怎么改） |
| `preview` / `demo` | 这次是不是预览 / 演示模式开着 |

每个 stage

| 字段 | 含义 |
|---|---|
| `stage` / `label` | 标识与中文名（`即将开始` / `今天的安排` / `明天的安排`） |
| `remind_id` | **整个位**的去重键，例如 `morning:2026-11-06`。同一天只念一次总览就靠它 |
| `items` / `count` | 条目 |
| `truncated` / `dropped` | 被 `limit` 截掉的条数。`truncated` 为真时建议补一句「还有 N 条，问我」 |

每个 item

| 字段 | 含义 |
|---|---|
| `remind_id` | **单条**的去重键。总览是 `morning:日期:条目id`，提前提醒是 `soon:条目id:开始时刻` |
| `id` | 条目 id（`cal-*` / `canvas-*` / `manual-*`）。要查详情、改删就把它拼进 `/api/item/<id>` |
| `kind` | `deadline`（截止）或 `日程` |
| `title` / `when_local` / `at` | 标题、给人看的一行、机器用的时刻（ISO） |
| `reason` | 为什么念它：`今日日程` / `今日截止` / `明日日程` / `明日截止` / `已过期未交` / `一小时内开始` |
| `source` / `course` / `location` / `all_day` | 照条目原样带过来，念不念可选 |
| `minutes_left` | 只有 `soon` 有：还有多少分钟开始 |

### 2.4 错误码

| 码 | 含义 | 终端该怎么说 |
|---|---|---|
| `400` | `stage` 不认识 / `limit` 不是整数 | 不用说话，这是调用方写错了 |
| `401` / `403` | 口令问题 | 和其它接口一样，提示「这台机器没配好口令」 |
| 连不上 / 超时 | 电脑端没开、不在同一网段 | 静默跳过这一轮，别念「提醒服务出错」 |

## 三、三个提醒位与时间语义

| 位 | 默认时刻 | 窗口 | 里面放什么 |
|---|---|---|---|
| `morning` | **08:00** | 08:00–12:00 | 今日日程 + 今日截止 + 已过期未交（最多 5 条） |
| `evening` | **22:00** | 22:00–次日 02:00 | 明日日程 + 明日截止 |
| `soon` | 滚动的 | 开始前 60 分钟内 | 每一条日程单独提醒，不带总览 |

几条必须知道的规则：

1. **是窗口，不是闹钟。** 8:00 到 12:00 之间任何时刻问，都算「早间」。
   十点才开机也还听得见今天的安排；12:00 之后就不再念了（那时候说「今天还有」意义不大）。
2. **「10 点」我按晚上 22:00 先做了。** 早上十点提醒明天的日程偏早，晚上十点才真会去想
   「明天要不要早起」。要是确实要上午十点，改一个字段就行：
   `config.local.json` 里加 `"remind_evening": "10:00"`，或者设环境变量
   `NAIWOZHU_REMIND_EVENING=10:00`，**不用改代码**。
3. **一小时内就要开始的日程不进总览。** 否则 8:00 的总览和 8:00 的提前提醒会把同一件事说两遍。
   它只在 `soon` 里出现一次。
4. **跨零点仍算前一天晚上。** 23:00 和次日 01:00 问，`evening` 都在，`remind_id` 还是
   `evening:<前一天>`——所以「明天」指的是同一个明天，不会过零点就换个日子。
5. **已过期未交只在早间提**，而且排在最前面（欠着的事比今天的安排更该先说）。
6. **全天日程按当天 23:59 结束。** 交我办导出的全天事件有时起止都是 00:00，
   照直比会在零点就被判成「已结束」，所以单独处理了。
7. **只用本机数据，不联网。** Canvas 截止是上次抓取的缓存；缓存旧不影响「该不该念」，
   只影响里面的条数。

设置怎么改（三处，优先级从高到低）：

```bash
# 环境变量（树莓派写进 systemd 最省事）
NAIWOZHU_REMIND_MORNING=07:30      # 早间时刻
NAIWOZHU_REMIND_EVENING=21:30      # 晚间时刻
NAIWOZHU_REMIND_BEFORE_MIN=30      # 日程开始前多少分钟
NAIWOZHU_REMIND_HOLD_MIN=180       # 一个窗口多长（分钟）
```

```json
// app/config.local.json（不用重启，下一次请求就生效）
{
  "remind_morning": "07:30",
  "remind_evening": "22:30",
  "remind_before_min": 45,
  "remind_hold_min": 180
}
```

`/api/status` 里的 `remind` 字段会回显当前生效的值，终端想知道就问它。

## 四、终端要改什么

### 4.1 `backend.py`：加一个方法

```python
def remind(self):
    """现在该念什么。拿不到就返回空，不要抛到播报层。"""
    try:
        r = self._get("/api/remind", timeout=3)      # 注意：3 秒就够，别用查询那套长超时
    except Exception:
        return None                                  # 连不上 = 这一轮不念
    if not isinstance(r, dict) or not r.get("ok"):
        return None
    return r
```

要点：

- 走 `GET`，带 `X-Access-Key: <BACKEND_TOKEN>`（`backend.py` 里已有这套头，照 `manual_delete()` 的写法来）。
- **超时要短**（2–5 秒）。它只是问一句「该念什么」，不该等 25 秒的连接超时——
  等待期间它还要能听见唤醒词。
- 失败**静默**：返回 `None`，主循环什么也不说。提醒服务挂了不该变成「出错了」的一句话。
- 非 `200`、非 JSON 都吞掉。这个接口的失败不该影响正常问答。

### 4.2 `assistant.py`：在主循环里轮询

现在的结构是「等唤醒 → 听一句 → 处理 → 播报 → 回到等唤醒」。提醒要插在**等唤醒**这段：

```python
next_poll = time.time() + 10            # 开机先等 10 秒，别和启动自检抢
spoken = set()                          # 本次开机已念过的 remind_id

while True:
    if time.time() >= next_poll:
        res = backend.remind()
        if res:
            for stage in res["stages"]:
                if stage["remind_id"] in spoken:      # 整段总览只念一次
                    continue
                if speak_stage(stage):                # 见 4.3
                    spoken.add(stage["remind_id"])
                    for it in stage["items"]:
                        spoken.add(it["remind_id"])
        next_poll = time.time() + 180                 # 三分钟问一次
    # ... 原来的 queue.get(timeout=1) / 等唤醒 ...
```

要点：

- **空闲才念。** 正在听、正在播报、正在多轮确认（`pending` 非空）的时候**不要插话**，
  把这一轮跳过，下一轮再说。插话会把用户正在说的话吞掉。
- 轮询间隔 120–300 秒都行；**它是问「现在该念什么」，所以问早了不会提前念**，
  服务端只在窗口内返回内容。开机 10 秒后的第一次也别急。
- 去重记在**内存**里就够了（一开机清空：重启后再念一遍今天的安排，比漏掉好）。
  要跨重启就去写一个小 json，但没必要。
- 语音唤醒时顺手把 `spoken` 里过期的键清掉（只保留今天的），不然跑一周会攒一堆。

### 4.3 `tts.py` / 话术：建议的模板

按你们现有的命名风格（`ok.delete` / `confirm.delete` …）加这些；没有的先用 `_missing.txt` 自愈那条路。

| 模板键 | 念什么 |
|---|---|
| `remind.morning.head` | 「今天的安排：」 |
| `remind.evening.head` | 「明天的安排：」 |
| `remind.soon.head` | 「马上要开始了：」 |
| `remind.item.schedule` | 「{时刻} {标题}」（`{时刻}` 用 `when_local` 里的时分，或 `minutes_left`） |
| `remind.item.deadline` | 「{时刻} 截止：{标题}」 |
| `remind.item.overdue` | 「还欠着：{标题}」 |
| `remind.empty.head` | 不用——没内容时服务端不返回这个位 |
| `remind.more` | 「还有 {n} 条，问我」 |
| `remind.none` | 不用——没到点就当没发生 |

拼句建议：

- 一个位最多念 **2–3 条**（`limit` 设 3 就自动截断，`truncated` 时说 `remind.more`）。
  全念完要半分钟，学生没耐心。
- 时刻只念时分，别念日期：说「九点，大学物理」，别把「十一月六日」也念进去。
  `when_local` 是给人看的整行，直接念会啰嗦。
- **不要念 `remind_id`、`id`、`reason` 这些字段名**，它们只给代码用。

### 4.4 一句话总结

> `backend.remind()` 拿候选 → `assistant` 空闲时按 `remind_id` 去重 → `tts` 按模板念 →
> 失败就静默跳过。终端**不重算时间窗、不判断该不该提醒**，那是电脑端的事。

## 五、给终端同学的 prompt（可整段复制）

> 电脑端加了「到点提醒」接口，仓库 `Jason-Pu-Junhao/naiwozhu-app`（`API.md` §2.6，
> 完整说明 `docs/交接_自动提醒.md`）。现在把终端从「只会被动回答」接到「到点主动开口」。
>
> **1）`backend.py`** 加一个方法 `remind()`：`GET /api/remind`，带现有那套访问口令头，
> 超时 3 秒，任何失败返回 `None`（不要抛给播报层）。
>
> **2）`assistant.py`** 在主循环「等唤醒」那段加轮询：每 180 秒问一次；
> `pending`（多轮确认）非空、正在听、正在播报时**跳过这一轮**；
> 用内存里的 `set` 记已念过的 `remind_id`（整段的 `stage.remind_id` 和每条
> `item.remind_id` 都记）；开机先等 10 秒再第一次问。
>
> **3）`tts.py`** 加模板：`remind.morning.head`、`remind.evening.head`、
> `remind.soon.head`、`remind.item.schedule`、`remind.item.deadline`、
> `remind.item.overdue`、`remind.more`；素材重跑一次 `gen_voice.py`。
>
> **4）** 一个位最多念 3 条；`stage.truncated` 为真时末尾补一句「还有 N 条，问我」；
> 没内容（`stages` 为空）时**什么都不说**。
>
> **5）** 别做的事：不要在终端算时间窗判断该不该念（服务端已经算了；
> 用 `preview=1` 能验证）、不要让它打断正在进行的多轮确认、失败不要播「出错了」。
>
> **6）** 自测：`python assistant.py --check` 通过；把电脑端时间改到 8:00 附近或
> 用 `curl` 看 `/api/remind?preview=1` 有内容；拔网线跑一轮，确认它只是不说话、不报错。

## 六、自测（两边都能跑）

电脑端命令行（不联网、不要令牌，最快）：

```bash
# 假装现在是早上八点
.venv/bin/python app/cli.py --remind --at "2026-11-06 08:00"

# 不管现在几点，三个位都算一遍
.venv/bin/python app/cli.py --remind --preview

# 每个位最多两条
.venv/bin/python app/cli.py --remind --preview --limit 2
```

网页端 / 终端视角：

```bash
curl -s "http://127.0.0.1:5173/api/remind" | python3 -m json.tool
curl -s "http://127.0.0.1:5173/api/remind?preview=1" | python3 -m json.tool
curl -s "http://127.0.0.1:5173/api/remind?stage=soon&limit=1" | python3 -m json.tool

# 局域网（树莓派）要带口令
curl -s -H "X-Access-Key: 你的口令" "http://192.168.1.23:5173/api/remind?preview=1" | python3 -m json.tool

# 确认它不联网：断网后照样有输出（缓存里的条目）
```

网页端设置页看不到提醒的开关（接口够用了）；要验证隐藏的条目不会被念，
在网页上「隐藏」一条交我办日程，再 `?preview=1` 看它就没了。

## 七、几条别做的事

1. **别做成电脑端主动推送。** 推送要常驻长连接，电脑一关就断；轮询在树莓派上最省事。
2. **别让 LLM 决定念不念。** 念什么、什么时候该念，全是确定性的规则；
   LLM 参与只会多一个「今天要不要提醒」的幻觉出口。
3. **别在终端重算时间窗 / 再筛一遍。** 两边各算一份，迟早不一致；
   要看规则对不对，用 `?preview=1` 和 `?at=` 在电脑端验证。
4. **别把「提醒」和「查询」混成一个接口。** `/api/query` 是回答问题，
   `/api/remind` 是到点开口，语义不同，失败处理也不同（一个要说话，一个要沉默）。
5. **别在没到点时播报。** 空 `stages` 就是「没事」，不是「提醒服务异常」。

## 八、已知限制（写清楚，免得被当成 bug）

| 情况 | 现在怎么样 |
|---|---|
| 电脑关机 / 不在同一网段 | 终端问不到，这一轮不念；开机后能补上当前窗口内的（8:20 开机仍会念今天的安排） |
| 过了窗口 | 12:00 之后不再念今天的安排、02:00 之后不再念明天的；要随时查用 `/api/query` |
| 电脑端单独使用 | 没有任何提醒——没有喇叭，弹窗也没做（刻意） |
| 提醒过没有、念过几次 | 电脑端不记录，全在终端内存里；重启终端会重念当前窗口内的内容 |
| 交我办条目改了时间 | 条目 id 由时间拼成，改期后 id 变了，`soon` 的 `remind_id` 也跟着变（同 `orphan_hides` 那个已知限制） |
| 截止没有「提前一小时」提醒 | 按需求只对**日程**做；要给截止加，改 `remind._soon_ready` 一处 |
